# 网页与微信小程序统一方案

## 判断

当前网页（含手机响应式布局）和原生微信小程序共用 Python API、交易核心、SQLite、模型配置和云端个人资料，但前端分别实现。小程序是功能缩减的首版，并非网页的完整移动形态。持续逐项补两份前端会反复产生差距。

建议目标栈为 uni-app + Vue 3 + TypeScript，使用普通 uni-app 编译 Web/H5 与微信小程序；现有 Python 后端、SQLite 和 runtime_core 保留。已完成共用前端首版迁移，源码位于 frontend/src，版本 0.2.0。云端默认网页已经切换到共用 H5，旧版 /legacy 保留备用；微信编译包已生成并导入开发者工具，界面编译通过；合法域名已生效，模拟器联网验证通过，真机验收待完成。

## 当前差距和统一验收范围

| 内容 | 网页已有实现 | 小程序现状 | 统一目标 |
| --- | --- | --- | --- |
| 对话历史 | 会话列表和恢复 | 最近六项操作菜单 | 完整列表、恢复与新会话 |
| 输入草稿 | 文本及附件恢复 | 页面内临时草稿 | 两端分别保留本机草稿；不默认跨端同步未发送内容 |
| 模型与回复 | 模型切换、流式回复 | 基本实现 | 同一模型能力提示、流式状态、失败恢复规则 |
| 图片/文件/录音 | 预览、播放、下载 | 上传及名称展示，录音转写 | 同一附件卡片、图片预览、音频播放、文件阅读/下载入口 |
| 知识库 | 分类、类型、待回看筛选、经典资料 | 分类、搜索与分页 | 同一分类和筛选、经典资料阅读 |
| 资料详情 | 状态、来源、关联资料、版本历史 | 通用字段及 JSON 文本 | 同一语义分段、状态说明、可追溯关系与版本历史 |
| 交易体系 | 完整纪律详情与层级阅读 | 每层前十条，基本规则列表 | 全量可访问的分层资料、规则详情和生效版本 |
| 界面状态 | 加载、空态、错误、交互细节 | 简化实现 | 同一设计规范与组件状态 |

“同一版本”指功能、数据解释、信息层级和发布版本一致。桌面网页使用侧栏和较宽详情面板，手机网页/小程序采用窄屏导航和独立详情页。不能要求设备间布局逐像素一致。

## 单一源码与边界

已创建 frontend/ 为唯一前端源目录，包含 pages/、components/、domain/、services/、platform/ 和 styles/。domain/ 负责资料类型、状态、分层与展示模型；services/ 负责后端协议及会话状态；components/ 共享资料卡片、状态标签、附件卡片和对话正文。Markdown 输出须经过可控解析，不直接跨端塞入网页 DOM。

platform/ 只处理真正的平台差异：浏览器 fetch 与微信 wx.request、Cookie 会话、流式分块、浏览器麦克风与 RecorderManager、选图/选文件、带认证的下载和音频播放、隐私授权及生命周期。上传到服务端仍使用现有接口，API 密钥不进前端。

H5 同源部署到现有 Python/Nginx 应用，避免引入不必要的跨域登录方案。微信开发者工具导入编译产物而非手工维护旧 WXML；构建产物不作为业务源码修改。小程序图片和录音仍通过带登录的下载适配器获取，不将私人附件改为公开地址。

普通 uni-app 已支持 Vue 3 和 Web/微信跨端；本项目不需要为了跨端引入 uniCloud、自建原生 App 或另一套数据库。Taro 也支持跨端，若已有 React 项目会更适合考虑；当前两端均是原生 JavaScript，并无 React 资产需要保留，选 uni-app 是工程判断，不是宣称框架性能必然更优。

## 迁移顺序

1. 以现有网页能力为验收基准，整理共享设计变量、资料展示模型和接口协议。
2. 建立跨端工程，先验证双端登录、中文流式回复、图片与录音上传和转写。这些平台差异是迁移的主要风险；先在两端跑通，再铺完整页面。
3. 共用组件迁移对话、知识库（含经典）、详情（含版本和来源）、交易体系；手机与桌面做响应式布局。
4. 使用临时业务库执行同一功能验收清单，核对所有资料可访问、编辑后的转写确实发送、模型切换不丢历史、待验证认识不会被显示为正式纪律。微信真机录音与文件选取必须单独验收。
5. 新版通过后切换网页发布目录和微信工程目录。旧版保留回退入口直到双端验收完成；不重建或迁移个人数据库，不改引擎原源码。
6. 为双端生成同一产品版本标识。前端改动发布 H5 并上传小程序版本；小程序审核和用户缓存意味着两端不能保证同时生效，需要兼容上一版本接口。后端模型配置调整则共用现有服务。
